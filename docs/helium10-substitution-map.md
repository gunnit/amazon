## 2. Gaps H10 newly fills (no source exists today at all)

1. **Sales/revenue estimates for third-party products** — the single biggest H10 differentiator. No `sales_estimate`/`monthly_sales`/`revenue` field exists anywhere (`schemas/market_research.py:42,151`; grep confirms zero); BSR is the only demand proxy (30% weight in comparison matrix, `market_research_service.py:331`). Amazon **cannot** provide this via any API. Requires new schema fields (`estimated_monthly_units`, `estimated_revenue`, `source`) fed by `search_products`/`get_listing_details`. Feeds #1, #3, #10, #12.
2. **Review count + rating for third-party products** — fields, matrix weights (0.2+0.2 = 40% at `market_research_service.py:332`), UI columns, and radar chart all exist and render N/A (`_extract_rating_and_reviews` at :1063 returns None,None on amazon.it essentially always). H10 data slots into existing `snapshot["rating"]`/`snapshot["review_count"]` with **zero schema/UI changes**. Cheapest visible win.
3. **Keyword / search-volume data** — no demand data anywhere (`generic_keywords` at `market_research_service.py:1260` is seller-typed backend keywords with no consumer; `BrandSearchTerm` is own-brand only). Cerebro/Magnet via `get_keywords_by_asin`/`get_keywords_by_keyword`/`analyze_keywords` is a net-new capability: volume, CPC, organic/sponsored rank, ABA data. Caveat: "keyword sales data" is documented NA-only — EU field quality needs live validation.
4. **Automated market share / competitor revenue** (#10 above) — today 100% dependent on a human uploading an export; the legacy mode aliases confirm that export historically came from H10 anyway. Automating it via `search_products` closes the loop.

Zero-changes downstream beneficiaries: PDF export (`exports.py:1244`), deck market block (`deck/blocks/market.py`), AI narrative — all pure consumers that light up once snapshots carry the data. One prompt carve-out needed: the AI's "never invent competitor revenue" rule needs a provenance-aware exception for `source=helium10` fields.

## 4. Integration notes

**Client location.** One client: `backend/app/core/helium10/client.py` (+ `mcp_client.py` transport), mirroring `backend/app/core/amazon/` — same pattern as `sp_api_client.py`: typed methods (`search_products`, `get_listing_details`, `get_keywords_by_asin`, …) returning plain dicts shaped like the existing snapshot fields, with internal rate/quota accounting. Every consumer above calls this one client; no per-service MCP plumbing.

**Auth/config — the biggest structural risk.** The MCP server uses OAuth-via-browser per H10 account (no API keys, no service accounts); sessions are revocable from H10 Settings and token lifetime is undocumented. For an unattended FastAPI backend this means: one shared H10 account for the whole platform (no multi-tenant key model), token stored encrypted (reuse the existing Fernet pattern for Amazon credentials), an admin re-auth flow for when the session dies, and settings in `app/config.py` (`HELIUM10_MCP_URL`, `HELIUM10_ENABLED` feature flag, monthly-budget knob). **Run a spike on token lifetime/headless refresh before building anything else.**

**Quota discipline (10,000 calls/month, platform-wide).** Complex research = 5-15 calls; one market-search enrichment of 20 ASINs can burn 20-100+. Mandatory: cache H10 responses in the DB (per ASIN+marketplace, ~24h TTL — matches H10's daily refresh), call H10 only for fields SP-API left empty, prefer batch tools (`compare_listings`, `analyze_keywords` ≤200), and enrich async/background (2-15s per call — never inline in `/market-search`). Keep SP-API as fallback everywhere so quota exhaustion degrades to today's behavior, not worse.

**amazon.it caveat (blocking).** MCP docs cite only US/UK/DE examples; IT coverage at tool level is **unverified**, and "keyword sales data requires Platinum+ for North America only" may degrade EU demand/sales fields. H10's UI tools do cover IT, so it likely works — but this platform is IT-first, so the go/no-go gate is an empirical probe with a live Diamond+ account: field-by-field output of `search_products`, `get_listing_details`, `get_keywords_by_asin` on known amazon.it ASINs (output schemas are not publicly documented either). One marketplace per request (fine — everything here is account-marketplace-scoped).

**Provenance.** All H10 values are modeled estimates refreshed ~daily. Label them (`source=helium10`, `estimated`) consistent with the existing `missing_data`/`price_unreliable` honesty pattern and the Brand Analysis Source/Confidence/Evidence direction; downgrade the market-share quality chip from 'exact' to 'estimated' when H10-fed.

**Implementation order (value ÷ effort, after the spike):**
1. **Spike (gate):** MCP client + OAuth lifetime + amazon.it field probe. Everything below depends on it.
2. **Brand Analysis market share** (#10) — highest value; synthesize `ParsedBrandExport` from `search_products` so metrics + deck need zero changes; kills the manual-upload dependency.
3. **Review count/rating fill** (gap 2 → feeds #1, #3, #7) — existing fields, existing UI, 40% of comparison matrix; smallest diff, most visible.
4. **Sales/revenue estimates** (gap 1) — new schema fields + `search_products`; unlocks #1, #3, #4, #12.
5. **Market Search replace** (#1) + price fifth-fallback (#2/#5) — same endpoint area, one wave.
6. **Competitor discovery replace** (#4) — Cerebro + Black Box; do the free salesRanks-sort interim fix immediately.
7. **Keyword/search-volume** (gap 3, #9, #11) — net-new capability, new UI surface, so last.

Free SP-API fixes to ship regardless of H10 (no dependency): `brandNames` param + cap raise in brand discovery (#6), image URL retention (§3), non-owned A+ `False`→`unknown` (#8), salesRanks sort (#4), `buyBoxPercentage` column (§3), competitor-tracker scheduler wiring (§3).
